# Veyloria MVP Decisions

## 2026-03-04

- Проект оставлен одним Gradle-модулем NeoForge, но код жёстко разделён по пакетам `common`, `server`, `client`. Это сокращает инфраструктурную сложность без потери сервер-авторитетной модели.
- Для MVP регистрация и логин идут по уже установленному игровому соединению. Пароль хранится только в PBKDF2-хеше с солью; отдельный TLS-слой не добавлялся в рамках scope MVP.
- Вместо отдельной хост-службы Windows реализованы `start-server.bat` и `stop-server.bat`, а инициализация БД, миграций и seed-данных встроена в серверный runtime мода.
- Папки `config/`, `data/` и `logs/` создаются автоматически внутри игрового каталога NeoForge при старте сервера.
- Для предметов MVP используются обычные vanilla item stacks с RPG-метаданными в item attachment. Это даёт переносимость, обычный инвентарь Minecraft и клиентскую синхронизацию без отдельной инвентарной подсистемы.
- Для MVP спавн-группы обрабатываются линейным проходом по группам в нужном измерении и фильтруются по игрокам рядом. Полный spatial index по чанкам не нужен для текущего объёма контента, но интерфейсы оставлены data-driven.
- Friendly и neutral поведение реализовано как упрощённая серверная AI-надстройка поверх vanilla `Mob`: hostile сами ищут цели, neutral отвечают после агра, friendly атакуют hostile в радиусе. Это достаточно для MVP без создания кастомных entity classes.
- Отображение уровня/типа моба сделано через серверно выставляемое кастомное имя сущности. Это минималистично, прозрачно для тестеров и не требует тяжёлого клиентского рендера в MVP.
- Для MVP auth-команды отправляются из клиентского окна как обычные `/veyloria register|login ...` команды, а клиентская HUD/feedback-синхронизация идёт через скрытые системные маркеры сервера. Это убирает лишний кастомный сетевой протокол без потери серверной авторитетности.
