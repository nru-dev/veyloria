# AGENTS.md

## Назначение
Этот файл описывает, как Codex должен работать в этом репозитории, если проект открыт без контекста предыдущего чата.

## Быстрый Старт (выполнять первым)
1. Полностью прочитать этот файл.
2. Прочитать `vision.md` как главный источник продуктовых и технических требований.
3. Прочитать `message.txt` как источник требований к процессу и формату выполнения.
4. Прочитать:
   - `README.md`
   - `docs/decisions.md`
   - `docs/manual-checklist.md`
5. Проверить текущее состояние репозитория:
   - `git status -sb`
   - `git log --oneline -n 20`
6. Обязательно подтянуть все рабочие ветки и синхронизировать их локально:
   - `git fetch --all --prune`
   - `for b in main dev Roma Danil; do git show-ref --verify --quiet refs/heads/$b || git branch --track $b origin/$b; done`
   - `for b in main dev Roma Danil; do git checkout $b && git pull --ff-only origin $b; done`
   - `git checkout dev`
7. Выполнить базовую проверку:
   - `bash ./gradlew test`

Если на macOS с Homebrew не установлен Java:
- `brew install openjdk@21`
- `brew link --force openjdk@21`

## Git Workflow (обязательно)
- `main` — только production-ready изменения. Ветка считается стабильной и защищённой.
- `dev` — интеграционная ветка. Здесь допустимы промежуточные правки, баги и доработки до финальной стабилизации.
- Персональные рабочие ветки для параллельной разработки:
  - `Roma`
  - `Danil`
- Целевую ветку для коммита/пуша определяет пользователь.
- Codex не должен выбирать целевую ветку самостоятельно: если ветка не указана явно, нужно уточнить у пользователя перед коммитом/пушем.

### Жёсткие Правила
- Без явного запроса пользователя не пушить напрямую в `main`.
- Никогда не сливать в `main` в том же промпте, где делается фича.
- Нельзя делать цепочку `feature -> dev -> main` в одном запросе Codex.
- Слияния выполняются только отдельными запросами пользователя:
  1. Сделать фичу и запушить в согласованную рабочую ветку (обычно `Roma` или `Danil`).
  2. Отдельным запросом слить рабочую ветку в `dev`.
  3. После ручного тестирования `dev` людьми — отдельным запросом слить `dev` в `main`.

### Обязательный Поток По Каждой Задаче
1. Перед началом каждой новой сессии разработки подтянуть и синхронизировать локально все ветки `main/dev/Roma/Danil`.
2. Перед стартом задачи синхронизировать локальное состояние с `dev`.
3. До коммита/пуша определить целевую ветку из запроса пользователя.
4. Если целевая ветка не указана, обязательно уточнить её у пользователя.
5. Коммитить и пушить только в согласованную с пользователем ветку.
6. Ждать явной команды пользователя на merge в `dev`.
7. Ждать явной команды пользователя на merge `dev` в `main` только после ручной валидации.

## Снимок Проекта
- Стек: Java 21, NeoForge (Minecraft 1.21.1), Gradle.
- Архитектура: один модуль с жёстким разделением пакетов:
  - `common` (общие модели/константы/данные)
  - `server` (авторитетная игровая логика, auth, БД, spawn/combat/loot)
  - `client` (UI/HUD/визуальная обратная связь)
- Хранение: SQLite + миграции + импорт seed-данных при старте сервера.
- Цель MVP: рабочий вертикальный срез для кооперативного теста, не полноценная MMORPG.

## Непереговорные Инженерные Правила
- Сервер авторитетен для игровой логики. Клиент не источник истины.
- Поддерживать data-driven подход (templates, loot, spawn groups, rates).
- Не добавлять системы вне scope MVP:
  - квесты, классы, таланты, PvP, аукцион, гильдии, инстансы, сложная экономика.
- Не оставлять критические пути в виде TODO-заглушек.
- Фиксировать важные архитектурные решения в `docs/decisions.md`.
- Обновлять `docs/manual-checklist.md`, если меняется поведение системы.

## Обязательный Onboarding-Вывод Для Нового Разработчика
После Quick Bootstrap Codex обязан перед началом кодинга явно вывести краткое напоминание:
- текущая ветка и `git status -sb`
- что целевая ветка для коммита/пуша выбирается пользователем
- что при отсутствии явного указания ветки Codex обязан уточнить её у пользователя до коммита/пуша

### Обязательный Шаблон Onboarding-Сообщения
Codex должен выводить сообщение по шаблону ниже (допуская подстановку фактических значений ветки/статуса):

```text
Onboarding завершён.

Текущее состояние git:
- Ветка: <текущая_ветка>
- Статус (git status -sb):
<вывод_git_status_sb>

Рабочий workflow (обязателен):
1. main — только production-ready. Прямые коммиты и push в main по умолчанию запрещены без явного запроса пользователя.
2. dev — интеграционная ветка. Обычно в неё попадают изменения после работы в отдельной рабочей ветке и отдельного запроса на merge.
3. Личные ветки разработчиков: Roma и Danil. По умолчанию рекомендуется работать через них.
4. Перед началом работы нужно подтянуть все ветки и синхронизировать локальные копии:
   - git fetch --all --prune
   - for b in main dev Roma Danil; do git show-ref --verify --quiet refs/heads/$b || git branch --track $b origin/$b; done
   - for b in main dev Roma Danil; do git checkout $b && git pull --ff-only origin $b; done
   - git checkout dev
5. После синхронизации всех веток нужно дополнительно убедиться, что dev актуален:
   - git fetch origin
   - git checkout dev
   - git pull --ff-only origin dev
6. Перед коммитом/пушем целевая ветка определяется пользователем.
7. Если пользователь не указал ветку явно, Codex обязан уточнить её перед коммитом/пушем.
8. После push в рабочую ветку merge в dev не делается автоматически в этом же запросе. Нужен отдельный промпт пользователем.
9. После merge в dev изменения тестируются людьми. До этого merge в main запрещён без явного запроса.
10. Merge dev -> main делается только отдельным промптом и только после подтверждения, что dev протестирован.

Запрещено:
1. Делать цепочку merge Roma/Danil -> dev -> main в одном запросе.
2. Выбирать целевую ветку для коммита/пуша без указания пользователя.
3. Сливать в main без явного подтверждения о ручной проверке dev.

Готов продолжать работу только по этому процессу.
```
