Твоя задача — полностью реализовать проект MVP RPG-мода для Minecraft, опираясь на файл vision.md как на главный источник требований.

1) Главный источник истины

Сначала полностью прочитай vision.md.

Считай vision.md одновременно:

продуктовым ТЗ,

техническим ТЗ,

рамками MVP,

списком ограничений.

Если в репозитории уже есть код, но он противоречит vision.md, ориентируйся на vision.md.

Если в vision.md есть неявные места, принимай разумные инженерные решения сам, не останавливая работу.

Любые важные допущения фиксируй в отдельном документе docs/decisions.md.

2) Цель

Доведи проект до состояния рабочего, собранного, структурированного MVP, соответствующего vision.md, где:

есть клиентская и серверная части;

сервер авторитетен для игровой логики;

работает регистрация/авторизация;

есть RPG-профиль игрока;

есть уровни, опыт, прокачка;

есть мобы, спавн, бой, смерть;

есть EXP, валюта, дроп;

есть кастомные предметы и экипировка на базовом уровне;

есть отдельные серверные рейты;

есть seed-данные и конфиги;

есть инструкции по запуску и проверке.

3) Принципы работы

Работай как ведущий инженер, а не как консультант.

Это значит:

не ограничивайся анализом — сразу после анализа начинай реализацию;

не задавай лишних уточняющих вопросов, если ответ можно получить из vision.md, структуры проекта или разумного допущения;

не останавливайся на полпути;

не оставляй критичные части как “TODO”;

не распыляйся на фичи вне MVP;

не переизобретай архитектуру, если она уже явно задана в vision.md.

4) Порядок работы

Следуй этому циклу до полного завершения:

Изучи vision.md.

Проанализируй текущую структуру репозитория.

Определи текущий стек, точки входа, систему сборки, зависимости.

Составь короткий поэтапный план.

Сразу начни реализацию по этапам.

После каждого этапа:

обновляй план,

проверяй сборку,

исправляй ошибки.

В конце:

прогони все возможные проверки,

добавь инструкции запуска,

дай сводку, что реализовано.

5) Что нужно сделать в первую очередь
Этап A. Анализ и каркас

Прочитай vision.md.

Изучи репозиторий.

Определи:

какой уже выбран mod loader;

какая версия Minecraft используется;

есть ли разделение на client/server/common;

есть ли БД, конфиги, миграции.

Если проект пустой или каркас слабый — создай минимально правильную структуру под MVP.

Этап B. Базовая архитектура

Приведи проект к чистой структуре с понятным разделением ответственности:

common — общие модели, DTO, константы, протоколы;

server — игровая логика, авторизация, БД, спавн, боёвка, лут, конфиги;

client — UI, HUD, клиентская синхронизация, отображение.

Если уже есть рабочая структура с другим именованием — можешь сохранить её, но логическое разделение должно быть таким же.

Этап C. Конфиги и данные

Реализуй:

загрузку конфигов сервера;

отдельный конфиг рейтов;

инициализацию БД;

миграции;

seed-импорт базовых данных;

безопасный запуск без ручной подготовки окружения.

Этап D. Авторизация

Реализуй:

регистрацию;

логин;

привязку аккаунта к minecraft_uuid;

хранение пароля только в хешированном виде;

блокировку игрока до авторизации;

загрузку RPG-профиля после входа.

Этап E. RPG-профиль

Реализуй:

уровень;

текущий EXP;

суммарный EXP;

валюту;

базовые статы;

сохранение/загрузку профиля;

серверную синхронизацию на клиент.

Этап F. EXP и уровни

Реализуй всю систему прокачки по vision.md:

уровни 1–80;

формулу EXP;

переходы между уровнями;

модификаторы по разнице уровней;

применение xp_rate;

корректную обработку нескольких level-up подряд.

Этап G. Мобы и спавн

Реализуй data-driven систему:

шаблоны мобов;

отдельные таблицы/сущности спавнов;

обычные/элитные/боссы;

friendly/neutral/hostile;

respawn и pack-спавн;

ограничения по активным мобам;

обработку только релевантных зон рядом с игроками.

Этап H. Бой

Реализуй серверную боевую логику:

сервер считает урон;

сервер считает HP;

сервер определяет смерть моба;

сервер определяет участников убийства;

клиент только отображает результат.

Этап I. Лут и валюта

Реализуй:

loot tables;

weighted selection без повторов;

количество предметов;

отдельные категории предметов;

персональный лут для каждого игрока;

валютный дроп;

применение currency_rate, resource_drop_rate, equipment_drop_rate.

Этап J. Кастомные предметы и экипировка

Реализуй:

шаблоны предметов;

категории предметов;

базовые статы экипировки;

редкости;

множители по редкости;

хранение метаданных предметов;

корректное отображение на клиенте.

Этап K. UI клиента

Реализуй минимум:

окно регистрации/логина;

HUD уровня и EXP;

базовое отображение информации о мобе;

визуально понятную обратную связь по получению EXP/лута.

Этап L. Финализация

Добавь:

инструкции запуска;

инструкции для локального теста с друзьями;

пример конфигов;

пример seed-данных;

чеклист ручной проверки.

6) Ограничения

Строго соблюдай:

Это MVP, а не полная MMORPG.

Не добавляй лишние системы, которых нет в vision.md, если они не нужны для работоспособности.

Не внедряй:

квесты,

классы,

таланты,

PvP,

аукцион,

гильдии,

инстансы,

сложную экономику,

неограниченный scope creep.

Делай только то, что нужно для тестового вертикального среза.

7) Технические требования к качеству

Код должен быть:

читаемым,

модульным,

без дублирования,

с понятными именами.

Любая игровая логика — на сервере.

Клиент не должен быть источником истины.

Все ключевые числовые параметры, которые по смыслу должны настраиваться, выноси в конфиги или data-driven таблицы.

Для схемы БД:

создай миграции;

не полагайся на ручное создание таблиц.

Для seed-данных:

добавь стартовые примеры мобов, лута, предметов и спавнов.

Добавь логирование для ключевых подсистем:

auth,

db,

spawn,

combat,

loot.

8) Если чего-то нет в репозитории

Если проект ещё не подготовлен, не останавливайся — создай всё необходимое сам:

структуру модулей;

конфиги;

миграции;

data models;

seed-данные;

документацию;

тестовые сценарии.

Но при этом сохраняй минимализм и не усложняй систему сверх требований vision.md.

9) Как действовать при неоднозначности

Если столкнулся с неоднозначностью:

Сначала ищи ответ в vision.md.

Потом — в существующем коде/структуре проекта.

Если ответа всё ещё нет:

выбери решение, которое лучше всего подходит для MVP;

зафиксируй это в docs/decisions.md;

продолжай работу без остановки.

Не зависай на выборе, если нет блокирующей причины.

10) Проверка результата

Перед завершением обязательно:

собрать проект;

прогнать все доступные тесты;

исправить ошибки сборки;

убедиться, что конфиги читаются;

убедиться, что миграции применяются;

убедиться, что seed-данные подхватываются;

убедиться, что ключевые сценарии покрыты кодом и/или инструкцией для ручной проверки.

Если полная runtime-проверка Minecraft в среде недоступна, тогда:

сделай всё, что можно проверить автоматически;

зафиксируй, что именно проверено;

добавь точную пошаговую инструкцию ручной проверки.

11) Формат твоей работы

Работай прозрачно и структурированно. В ходе выполнения:

сначала покажи краткий анализ текущего состояния;

затем покажи поэтапный план;

потом переходи к реализации;

после крупных изменений кратко фиксируй прогресс;

в конце дай итоговый отчёт:

что реализовано,

какие файлы созданы/изменены,

какие проверки выполнены,

что осталось только для ручной валидации.

12) Критерий завершения

Считай задачу завершённой только когда:

реализация соответствует vision.md;

проект структурно приведён в порядок;

критичные подсистемы не оставлены как заглушки;

есть конфиги, БД, seed-данные, документация;

проект можно собрать и подготовить к тесту с друзьями;

результат доведён до максимально полного рабочего состояния в рамках MVP.

Начни с:

чтения vision.md,

анализа репозитория,

составления краткого плана,

и сразу переходи к реализации.
